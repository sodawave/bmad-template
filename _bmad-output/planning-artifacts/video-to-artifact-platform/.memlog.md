# Memory Log — Video-to-Artifact Platform (MVP)

- **Created:** 2026-10-13
- **Parent ADRs:** ADR-001, ADR-002
- **Architecture Spine:** `ARCHITECTURE-SPINE.md`

## Decisions & Rationale

### Decision 1: Four-Ring Clean Architecture (Strict)
- **Qué:** Enterprise Core → Application Business Rules → Interface Adapters → Frameworks & Drivers.
- **Por qué:** ADR-001 exige Clean Architecture como estándar obligatorio. El MVP es lo suficientemente simple para demostrar los cuatro anillos sin sobrecargar la estructura.
- **Binds:** Todas las historias futuras mapean sus unidades a un anillo; los checks de import/dependency verifican la regla antes de evidencia.
- **Prevents:** Frameworks, ORMs o servicios externos definiendo reglas de negocio; referencias cruzadas desde el core hacia detalles externos.

### Decision 2: MVP Scope — Transcript Extraction Only
- **Qué:** Ingestar video → extraer audio → transcribir → producir artifact de texto (transcript o resumen básico).
- **Por qué:** ADR-002 define un MVP simple y verificable. El transcript es el artifact más directo; otros tipos (video, audio) se posponen.
- **Binds:** El pipeline tiene exactamente 4 etapas: ingest → extract → analyze → produce.
- **Prevents:** Expandir el MVP a streaming, UI web, multi-modal artifacts o autenticación antes de validar la funcionalidad base.

### Decision 3: LLM/Tool-Based Analysis (No "Can't See Video")
- **Qué:** Garantizar que el procesamiento de video use un LLM o cadena de herramientas para análisis (no reglas hardcodeadas).
- **Por qué:** ADR-002 exige que el sistema "vea" el video mediante análisis real (transcripción + LLM), no un fallback de "no puedo ver video".
- **Binds:** El caso de uso `AnalyzeWithLLM` es obligatorio en el pipeline.
- **Prevents:** Reglas hardcodeadas para generar artifacts; omitir el análisis LLM como atajo.

### Decision 4: Local Storage for MVP (Deferred S3)
- **Qué:** Usar filesystem local para persistir artifacts en el MVP.
- **Por qué:** Simplifica la implementación inicial; S3 o BD se añaden como adapter futuro sin cambiar el core.
- **Binds:** `ArtifactStorageAdapter` implementa `IArtifactRepository` con backend de filesystem.
- **Prevents:** Acoplar el core a un storage específico; cambiar de local a S3 requiere solo reemplazar el adapter.

### Decision 5: CLI Interface for MVP (Deferred Web UI)
- **Qué:** Interfaz de línea de comandos (Node.js o Python) para usuarios.
- **Por qué:** MVP no necesita UI web; CLI es suficiente para validar el pipeline de procesamiento.
- **Binds:** `CLIInterface` es un driver en Frameworks & Drivers; no afecta el core ni los use cases.
- **Prevents:** Construir una UI web antes de validar la funcionalidad base; acoplar el core a un framework UI.

## Deferred Decisions (Future Spine)

| Decision | Cuándo abordar |
|----------|----------------|
| Multi-modal artifacts (video, audio, imágenes) | Después de validar transcript MVP. |
| Real-time streaming | Cuando se requiera procesamiento en vivo (no batch). |
| User authentication/authorization | Cuando haya múltiples usuarios o multi-tenancy. |
| S3/distributed storage | Cuando el volumen de artifacts requiera escalabilidad. |
| Web/Mobile UI | Cuando la CLI no sea suficiente para usuarios finales. |

## Notes for Future Agents

- **Clean Architecture is non-negotiable:** Every story must map to one of the four rings. Import/dependency checks verify the rule before evidence is accepted.
- **MVP scope is narrow by design:** Do not expand to streaming, multi-modal, or UI until the transcript pipeline is verified.
- **LLM analysis is mandatory:** The `AnalyzeWithLLM` use case cannot be skipped or replaced with hardcoded rules.
- **Adapters are swappable:** Replace any adapter (transcript service, LLM client, storage) without changing core entities or use cases.
